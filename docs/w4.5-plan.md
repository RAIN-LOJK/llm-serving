## 0. 一页纸

- **目标**：把 attention 路径从「逐请求 SDPA prefill + gather decode」升级为
  「packed whole-prompt prefill（FA2 varlen）+ Triton block-table decode」，seat/paged 两臂共用接口。
- **成功定义**：
  1. E0 正确性过（golden 64/64；packed==serial；Triton==dense oracle）。
  2. E1 容量不变（seat 9 vs paged 28）；E2 的 internal frag 仍 0.55%。
  3. E2 paged decode `step_ms` ≤ seat（目标 ≤1.0×，接受 <1.15×），gather 流量归零。
  4. E3 packed prefill 在同一 workload 下 TTFT p99 改善 ≥ 预注册线，且 p50 不显著恶化。
  5. E4 端到端 paged tok/s ≥ seat，且 ≥ `W4-0009` 的 358.18 tok/s（同 trace、同预算）。
- **时间盒**：G1/G2 1–2 天；实现 7–9 天；重跑 2–3 天；合计 ≈2 周。
- **止损**：G1 不过 → 不开 W4.5，decode 走 `W4-0010`，直接 W5；G2 不过 → 只做 packed prefill
  （W4.5a），C4 维持 W4 负结果；两周不绿 → 砍 prefill 保 decode。

- **做什么**：0.6B、D=128，pack 2/4/8 条 prompt（长度 128–1517），与逐序列 SDPA 对比：

## 3. 实验细节

### 3.1 E0 · 正确性

**E0a packed vs serial（脚本/单测）**
- 2/4/8 条 prompt，长度覆盖 128/512/1517；同一 model、同一 prompt 顺序、bf16。
- 比对：每请求最后 token 的 logits `max|Δ|`、greedy token ids；确认没有跨请求 attention 泄漏
  （改 request 0 的 token 不影响 request 1 的 logits）。
- 失败即停：packed prefill 的 `cu_seqlens`/位置编码有错，先修再谈性能。

**E0b Triton vs dense oracle（脚本/单测）**
- 随机 block table（含复用块、非连续块）、seqlen 1..L、页边界（seqlen % 16 != 0）、
  GQA group 2 与 8、D=128/256、bf16。
- oracle：`PagedPool.gather` + `hand_baddbmm`（只读，不进生产）。
- 比对：output `max|Δ|`、argmax；NaN/Inf 检查。
- 这是 kernel 的数值规格；不过不许跑 E2/E4。

**E0c 端到端 golden（1 run）**
- `W45-0001`：paged + packed + Triton，s01、`max_new_tokens=64`、`max_batch=1`、64 块。
- 判据：`scripts/check_paged_golden.py` 对 `tests/golden/qwen3-0-6b/0001` 逐 id 全等（64/64）。
- golden 不过：先判是否 near-tie（fp32 oracle），不静默重生成。

### 3.2 E1 · 容量守卫

- `W45-0002` / `W45-0003`：复制 W4 的 fill-only 配置，只改 stage/id；同 seed/rate/requests/
  budgets/prompts（`trace_sha256` 相同），两臂只差 `[engine]`。E1 固定 `prefill="serial"`
  （与 W4 同路径），只验证 allocator；packed prefill 的峰值由 E4 看。
- 判据：seat 9 行、paged 28 条、3.111×；paged `kv_total ≤ 1640 MiB`。
- 这一组不产生新结论，只证明注意力路径改动没碰分配器；不过就停，先查 allocator。

### 3.4 E3 · packed prefill

- `W45-0006` / `W45-0007`：seat 路径，static、closed、8 条 mixed prompt、B=8、

## 4. 机制设计

### 4.1 packed prefill

- **接口**：`flash_attn_varlen_func(q, k, v, cu_seqlens_q=..., cu_seqlens_k=...,
  max_seqlen_q=..., max_seqlen_k=..., softmax_scale=..., causal=True)`；q/k/v 为 packed
  `[total_tokens, H, D]`；**不传 `block_table`**（不读 paged cache），因此不受 FA2 的
  256 page 约束。
- **打包**：step 开始时按 FIFO 取已到达的请求，填到 `max_prefill_tokens`（默认 8192）或
  `max_batch` 上限；队头放不下就单独成组，不跳队、不等满。一个 prompt 不拆（无 chunk）。
- **顺序**：同一 step 先跑 packed prefill 的 group(s)，再跑现有 decode batch；**不混一个
  forward**。prefill 仍会延迟同 step 的 decode，这是已知代价，不引入 chunked。
- **KV 写入**：每层算完 k/v 后按 slot map 写入 seat 行或 paged 块；prefill 不用
  `block_table` 读。seat 与 paged 共用同一 varlen 计算，只差写入目标。
- **logits**：只对每组每个请求的最后一个 token 算 lm_head（`cu_seqlens[1:] - 1` 取 hidden），
  不物化 `[total_tokens, vocab]`。
- **首 token**：每组的 last-token logits 一次 lm_head + **批量 greedy argmax**，`t_first` 对同组
  统一戳；不要逐请求采样循环，否则 `prefill_shared` 不再是共享时间，TTFT 恒等式会破。
- **位置**：packed 顺序为 request-major；每个 token 的 position 是请求内位置，RoPE 逐 token 应用。
- **配置**：`[engine].max_prefill_tokens = 8192`；临时 `[engine].prefill = "serial" | "packed"`
  只用于 E3（见 §5）。

### 4.2 Triton decode

- **签名**（建议）：
  ```python
  paged_decode(q, k_cache, v_cache, block_table, seqlen, *, scale, block_size) -> out
  # q: [B, H, D]（每请求 1 token）
  # k_cache/v_cache: [n_blocks, block_size, H_kv, D]
  # block_table: [B, max_blocks] int32；seqlen: [B] int32
  # out: [B, H, D]
  ```
- **算法**：grid 按 `(B, H)`；`h_kv = h // (H // H_kv)`；按页循环 `ceil(seqlen/bs)`，加载
  K/V `[bs, D]`，`qk = q @ K.T`，只 mask `col >= seqlen`（最后页部分有效），online softmax
  （fp32 `m`/`l`/`acc`），输出 bf16。**无 causal mask、无零块、无 `lpad`**。
- **起点**：一页一迭代（`BLOCK_N=16`）先保证正确；若 loop 开销明显，再合并 2–4 页/瓦片；
  `B*H` 不足或 L=8k 时再加 split-K（partial `m/l/acc` + 第二 kernel 合并）。
- **形状**：page 16/32 都支持，W4.5 固定 16（与 W4 C1 可比）；D=128/256 用 constexpr 特化；
  GQA group 2/8。
- **集成**：decode 前把新 token 的 k/v 写入池（slot map），kernel 只读；`PagedAttention.decode`
  调用；`model.layers` 不感知 block table；非 CUDA 显式 `RuntimeError`，MPS 测试 skip。

### 4.3 接口与调度

- 新增 `PagedAttention` 门面（名字可调）：
  - `prefill(q, k, v, *, cu_seqlens, max_seqlen, writer)`：FA2 varlen + 逐层写入；
  - `decode(q, pool, block_table, seqlen)`：Triton kernel。
- seat 路径：prefill 走同一 varlen 计算，writer 写 `KvSlab`；decode 保持 `hand_baddbmm`
  （W2/W3 基线不动）。
- paged 路径：prefill 写 `PagedPool` 块；decode 走 Triton；`PagedPool.gather` 只留 oracle。
- **不回退**：paged 在 CUDA 上必须走 kernel；seat/paged 由 `[engine].impl` 显式选择，不按
  可用性自动切换。

### 4.4 测量契约

- 每请求：`t_arrival`、`t_admitted`、`t_prefill_start`、`t_first`、`t_finish`。
- 定义：
  - `queue_ms = t_admitted - t_arrival`
  - `pack_wait_ms = t_prefill_start - t_admitted`
  - `prefill_shared_ms = t_first - t_prefill_start`（同组共享）
  - 恒等式：`ttft_ms == queue_ms + pack_wait_ms + prefill_shared_ms`（同组内逐请求成立；
    多 group 时按 `group_id` 取各自的 shared）。
- 串行臂：`pack_wait=0`，退化为 W3 的 `ttft == queue + prefill`；C2 的旧口径只在串行臂判。
- `t_first` 同组统一：每组 last-token logits 一次 argmax；若某天必须逐请求采样，`sample_ms`
  单独记，不混进 `prefill_shared`。
- step row 增加：`prefill_groups`、`prefill_shared_ms`（sum）、`pack_wait_ms`（sum/分布）、
  `prefill_ids_per_group`；`host_gap` 公式同步。
- 报 p50/p95/p99/max；不报单一均值。

## 10. 风险与 PITFALLS

- **FA2 安装/编译**：torch 2.8 cu128；wheel 优先，源码编译限时；不过就是 G1 失败，不硬啃。
- **FA2 256 page 约束**：只在使用 `block_table` 时触发；W4.5 的 prefill 不读 paged cache，
  所以安全。**不要**把 `flash_attn_with_kvcache(block_table=...)` 接进来（会废掉 bs16）。
- **last-token logits**：packed prefill 只对每请求最后一个 token 算 lm_head；全量 logits 会
  在 8192 token × 151936 vocab 上爆内存/带宽。
- **TTFT 归因**：packed 的 p50 可能变差、p99 变好；只报均值会掩盖。`pack_wait` 必须单独记。
- **Triton 页循环**：最后页按 `seqlen` mask；block table int32；不要依赖零块；D=256 要特化。
- **控制臂泄漏**：`prefill=serial` 不得成为生产回退；阶段结束删，`grep` 确认无引用。
- **跨 commit 基线**：E4 对 `W4-0006/0009` 的比较要标 commit；不混 M1/4090 数字。
- **PITFALLS 候选**（收口时按实际踩坑编号）：
  - P-40 packed prefill 的 TTFT 是共享时间，p50/p99 可能反向；
  - P-41 FA2 paged 的 256 page 约束不适用于 varlen prefill，但 prefix cache 一引入就适用；
  - P-42 Triton decode 的最后页/块表 dtype/无零块；
  - P-43 static 臂也从 packed prefill 受益，continuous 比值会被稀释；
  - P-44 超 `max_prefill_tokens` 的长 prompt 单独成组，不是 chunked。
